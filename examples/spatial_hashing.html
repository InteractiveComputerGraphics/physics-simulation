Spatial hashing for collision detection

Bounding volume hierarchies (see the BVH example) are very efficient for rigid objects: the hierarchy is built once and only refitted when the object moves, and refitting a rigid object keeps all boxes tight. For deformable objects, this no longer works well. After refitting, the boxes still contain their primitives, but primitives that were close to each other in the beginning (and therefore were grouped together in the tree) can drift apart, so the boxes grow and overlap more and more and the tree has to be rebuilt from time to time. Self-collisions are also difficult, since a deformable object's tree must be tested against itself. Watch the statistic "Refitted BVH area" (the summed area of all boxes of the refitted tree relative to a freshly built tree) and switch on "Show BVH boxes" to see this.

Spatial hashing [THM+03] avoids a hierarchy altogether. It uses a uniform grid, which is rebuilt from scratch in every time step at very low cost, and it handles collisions between different objects and self-collisions in the same way.

Uniform grid and hash function

Space is divided into square cells (cubes in 3D) of size $l$. A point $\mathbf x$ lies in the cell with the integer coordinates $$(i, j) = \left(\left\lfloor \frac{x}{l} \right\rfloor, \left\lfloor \frac{y}{l} \right\rfloor\right).$$ Primitives can only collide if they occupy common cells. Storing an explicit grid would require memory for the whole simulation domain, although only a few cells are occupied, and the domain would have to be known in advance. Instead, the cells of the conceptually infinite grid are mapped to a hash table with $n$ buckets by a hash function, e.g. $$h(i, j, k) = \big( (i \cdot p_1) \oplus (j \cdot p_2) \oplus (k \cdot p_3) \big) \bmod n$$ with the large primes $p_1 = 73856093$, $p_2 = 19349663$, $p_3 = 83492791$ and the bitwise exclusive or $\oplus$ [THM+03] (in 2D, the $k$-term is omitted). The memory only depends on $n$, not on the size of the domain. Different cells can be mapped to the same bucket; such hash collisions do not cause wrong results but only additional candidates, which are rejected by the subsequent tests. Switch on "Color cells by hash value" and select a small table size: cells with the same color share a bucket.

The algorithm

Following Teschner et al. [THM+03], collisions are detected as vertices that penetrate a triangle (in 3D: a tetrahedron) in two passes:

  1. Insert all vertices: for every vertex, compute its cell and its hash value and append the vertex to the corresponding bucket. Instead of clearing the table in every step, each bucket stores a time stamp and is treated as empty if the stamp is outdated.
  2. Query all triangles: for every triangle, compute its axis-aligned bounding box (AABB) and the range of cells it overlaps. For each of these cells, compute the hash value and test all vertices in the bucket:
    • skip vertices of the triangle itself (and vertices that were already tested for this triangle, which happens if two cells are mapped to the same bucket),
    • reject vertices outside the triangle's AABB (this also removes all vertices that only got into the bucket by a hash collision),
    • perform the exact point-in-triangle test for the remaining vertices.

Both passes are linear in the number of primitives (for well-chosen parameters), there is no preprocessing, and the cost does not depend on how much the objects deform. Since every triangle is tested against all vertices in its cells, regardless of the object they belong to, self-collisions are detected without any extra effort (select "strong" deformation). Both passes are also easy to parallelize.

Parameters

  • Cell size $l$. If the cells are too small, every triangle overlaps many cells, so many buckets have to be read. If they are too large, each cell contains many vertices that do not collide but must be tested. A cell size in the order of the average edge length is a good choice [THM+03]. Compare the "bucket tests" for the different cell sizes.
  • Table size $n$. A small table causes many hash collisions and long buckets. A table that is larger than the number of vertices (load factor $< 1$) keeps collisions rare. Prime table sizes distribute the hash values more evenly.
  • Primitive sizes. A uniform grid works best if all primitives have a similar size. A very large triangle covers many cells; very different sizes would require several grids. BVHs adapt automatically to non-uniform sizes and distributions.
